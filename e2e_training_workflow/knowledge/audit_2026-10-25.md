## 一、主要发现（按影响排序）

### 1. QualityGate 种子扩展会覆盖"复用未证明"的 fail-closed 判定，无效复用最终可能显示 CLEARED
- **严重度**：high（ORCH-A3）
- **位置**：`training_workflow.js:1741-1764`
- **问题**：
  - 1741 行检测到 `reuse_check.valid !== true` 时，把 quality_gate 改写为 NOT CLEARED。
  - 但 1748 行的扩展条件判断的是原始的 `q.quality`（仍为 INCONCLUSIVE），于是照样启动 5-seed 扩展。
  - 1762 行再用扩展结果 `qx` 整体替换 quality_gate，之后没有再套用 reuse 守卫。
  - 结果是 `cleared=true`、`status 'ok'`，合并判定还把未经证明的复用 REF legs 一并 pool 进去。该路径已由 dry-run 桩 P3 复现。
- **修复**：先算出 `reuseOk`，扩展条件必须要求它为真；扩展完成后对合并判定再执行一次 reuse 守卫。
- **对记录结果的影响**：P0-4m 和 P0-4p 已人工核对 GEAK_OVERLAY_SHA，结论成立，因此没有已记录结论被推翻。但这是 outcome gate 上的 fail-open，属于最需要先修的一条。

### 2. quality_reuse.py 只比对 train.log 参数表，看不到 overlay / env / harness / image，也从不检查 ctrl 臂
- **严重度**：high（ID-3 与 HFC-1 合并）
- **位置**：
  - `scripts/quality_reuse.py:42-51, 72-96`
  - `training_workflow.js:1741-1745`：直接采信 agent 上报的 `reuse_check.valid`，不自行重算
  - `roles/training_director.md:158-165`
- **问题（已复现）**：
  - 用 bare REF 对 8-overlay 的 hf8 cand（`qabhfchk_1017_203738_ref` vs `qabhfbal_1023_143846_cand`，`--allow hf_balance_tokens`）检查，返回 `valid: true`。
  - 用 bare 对 s4（`qabpv_1015_191546_ref` vs `qabbis_1015_234954_s4`）检查，同样 valid。
  - 在 182 个 qab legs 中，有 45 组参数表完全相同、但 overlay 或 env 集合不同。
  - ctrl70 臂经 `link` 接入后，从未进入 `check`。
  - 反方向也有问题：overlay 日志行被拼接进参数表（seed 3345 的 add_qkv_bias），造成误拒。probe_summarize 用 `_SPLICE` 处理了这个问题，quality_reuse 没有。
- **修复**：
  - `check` 增加逐 seed 比对：probe header 的 workload_identity 与 implementation（GEAK_OVERLAY_SHA、全部 `env:*` 键，减去 `--allow` 和声明允许变动的 overlay slot）、harness（rocm_compat / overlay_train / hf_sft / image_id），以及 data sha。
  - ctrl 臂按其自身允许的差异（例如 lr）单独校验。
  - 复用 probe_summarize 的 `_norm` / `_SPLICE`。
  - 由 orchestrator 自己运行 quality_reuse，不再读取 agent 上报的 JSON。
- **对记录结果的影响**：
  - DECISIONS 4.63 声称该工具能"证明复用 legs 与 cand 配方一致"，这一说法不成立，实际只覆盖参数表。
  - 4.70（P0-4o）复用了 `qabavg_1016_175311_cand`（digest_schema 4，harness None），新 legs 跑的是 rocm_compat 修改之后的版本，证据强度需降级。
  - P0-4m 和 P0-4p 经人工 SHA 核对后仍然成立。

### 3. Packing（Class-B）接受路径完全绕过 legUsable / comparable / verifier
- **严重度**：high（ORCH-A4）
- **位置**：`training_workflow.js:1278-1306`
- **问题**：
  - 该分支只读取 agent 上报的 `packing_gate.pass` 和 `comparison_tokens.delta_pct`。
  - P7 中 ref 为 failed+contaminated、cand 为 failed+hang，仍判 win 并 `accepted_config 'packing'`。
  - 被接受的 packing flags 随后经 acceptLever 合并进之后的每一条 leg。
  - 这是全局收益最大的杠杆（+258%），却是唯一完全建立在自报数字上的 gate。
- **修复**：先要求 `legUsable(ref/cand).ok`；由 gate_verifier 从 leg 目录重算 `compare_legs_tokens.py`（可行的话 pack_gate 也重算）；只按重算出的 delta 接受。
- **对记录结果的影响**：未发现已记录的 packing 接受是走这条自动路径得出的。但凡是经此路径接受的 packing，都应用 verify_gate 补做一次重算。

### 4. 身份快照是手工维护的 argv/env 白名单，大量改变数学或速度的设置不进入任何 digest
- **严重度**：high（ID-1）
- **位置**：
  - `scripts/train_probe.py:353-434`（`_IDENTITY_*_KEYS`）、`:443-459`、`:530-532`（只捕获 3 个 NVTE_* 变量）
  - `scripts/probe_summarize.py:187-194`（`identity_vs_realized` 只遍历已捕获的键）
  - `adapters/megatron.sh:89-109`（argparse 对重复参数取最后一个值）
- **问题（已复现）**：以下改动的 cfg / impl digest 与 base 完全相同：
  - argv：`--fp8-format hybrid`、`--tp-comm-overlap`、`--use-precision-aware-optimizer --exp-avg-dtype bf16`、`--optimizer sgd`、`--no-bias-swiglu-fusion`
  - env：`NVTE_CK_USES_BWD_V3=0`、`NVTE_CK_IS_V3_ATOMIC_FP32=0`、`PYTORCH_TUNABLEOP_ENABLED=1`、`NCCL_ALGO=Tree`
  
  `is_impl_key` 会把所有 NVTE_* 归为实现键，但采集端只采 3 个，正是文件注释里警告过的"列在一处、哪里都没采"。v4 和 v5 都是一次修一个键，同类缺陷反复出现。
- **修复**：
  - 从 Megatron 和 hf_sft 打印的 realized 参数表派生 identity：除显式的路径类 / 运行长度类清单外全部纳入 digest。
  - 用显式的 workload-vs-impl 映射表，遇到未映射的键 fail-closed。
  - bench_train 拒绝无法被捕获的 `--extra-train-args` / `--extra-env`，或者把全部 NVTE_ / NCCL_ / RCCL_ / HSA_ / PYTORCH_ / TORCH_ 变量都纳入。
- **对记录结果的影响**：没有具体结论被推翻。这是潜在的身份漏洞，同时影响跨 session 的基线复用。

### 5. main_grad 契约的适用性靠 target_callable 子串匹配，组合型 overlay 被判"不适用"后放行
- **严重度**：high（G-1）
- **位置**：
  - `scripts/main_grad_contract.py:418-444`（`head_for`）
  - `training_workflow.js:1558-1564`（接受 `mgc.applicable === false`）
- **问题**：
  - `mlp_fc1_swiglu` 的 target 字符串是 `...MLP.forward [_LayerNormLinear (RMSNorm+fc1) -> ...]`，不包含 `layernorm_linear:_LayerNormLinear`，因此被判 NOT APPLICABLE。
  - 但它的 candidate_bind 重绑了整个 `MLP.forward`，其中包含写入 main_grad 的 fc1 fused-wgrad。
  - DECISIONS 4.50 已经说明，L0 看不到 bf16 截断的 wgrad，这个契约正是为此而设。此处等于 fail-open。
  - grad_tail scaling 这个例子不成立：它不是 wgrad 累加，判为不适用可以接受。
- **修复**：按累加路径判定适用性。target 或 capture 中出现 `_LayerNormLinear` / `_Linear` / `main_grad` / gradient_accumulation_fusion 中任一时，fail-closed（applicable=true、passed=false、"no head"）。为组合型 overlay 增加 head，或要求 Auditor 显式指定 head。
- **对记录结果的影响**：目前没有已接受的组合型 overlay（mlp_fc1_swiglu 已因 inf grad 死亡），未发现被推翻的结论。建议对 s8a22 的 8 个 overlay 的 task meta 跑一遍 `head_for`，确认当时判定为 applicable。

### 6. 吞吐 gate 只看 per-step ratio 的中位数，没有 sum / wall 否决，校准也测不到这一类问题
- **严重度**：medium（MS-1）
- **位置**：
  - `scripts/compare_legs.py:139-148`
  - `training_workflow.js:597-645`（gateVerdict 不读取 `wall_delta_pct`）
  - `scripts/calibrate_band.py:261-275`（均匀注入）
- **问题**：
  - 合成实验：真实 leg `repin1021_v6_bare` 中，4/22 步慢 10%、其余快 1%，gate 判 `win +1.01%`（band 0.30%），真实总时间却是 -0.996%。
  - 由 stall 导致的符号翻转已在 4.41-4.43 记录（`comm_1016` D1→E1 paired +1.15% / wall -0.13%）。
  - 未记录的部分有两点：零 stall 的异质 per-step 效应同样会翻转符号，以及校准只做均匀注入，测不到这种情况。
  - s8 栈在 gbsx_1015 的所有 pair 上，paired 为 +21.5..21.8%，wall 为 +18.8..20.2%。
- **修复**：在同一对齐窗口上计算 `sum(ref)/sum(cand)`。当它小于 0（或小于 delta − band）时拒绝 win，或把 wall delta 升级为否决条件。calibrate_band 增加异质注入。
- **对记录结果的影响**：
  - 不推翻 4.41-4.43 的方法选择。
  - 交付物 headline 的 paired 增益比 wall 增益高约 1.5-3 pp，对外引用时应同时给出 wall 数字。
  - 建议排查已接受的杠杆中是否有 wall_delta < 0 的情况。

### 7. 种子扩展使非劣效检验成为两次查看且没有 alpha spending，实际 type-I 约 8.4% 而非 ~5%
- **严重度**：medium（G-4）
- **位置**：
  - `training_workflow.js:47`（QUALITY_EXTEND_SEEDS 默认开启）、`1744-1763`
  - `scripts/quality_ab_final.py:149, 159`
- **问题**：
  - 两份独立模拟一致：在"恰好差一个 margin"的情况下，单次检验的通过率约 5%，加上扩展后整体约 8.1-8.5%。
  - 4.45（1022 attention）走的正是这条路径：n=5 INCONCLUSIVE，n=10 PASS。
- **修复**：采用 group-sequential 边界（Pocock 每次约 0.029 单侧，或 O'Brien-Fleming），把 look 序号传给 quality_ab_final；或者在 4.44 中如实写明约 8.4%。
- **对记录结果的影响**：
  - 4.44 中"约 5%"的保证不成立。
  - 4.45 和 4.70（n=10，经扩展）的显著性水平应改述为约 8%。
  - 结论本身未被推翻。4.70 的 upper +0.00284 离 margin 0.00515 仍有余量。

### 11. 编排层的不变量只写在 prompt 中：kernel gate 不绑定 workload / carried config，stacked baseline 不校验
- **严重度**：medium（ORCH-A1 与 ORCH-A6 合并）
- **位置**：
  - `training_workflow.js:1411, 1536`（overlayShaCheck）
  - `489-560`（comparable 只比较 ref 和 cand）
  - `1243/1306/1372`（acceptLever 之后 refLeg 不更新，也不 re-profile，与 1599 行注释不符）
  - `1081-1099`
- **问题**：
  - P2 / P10：ref 和 cand 跑在不同 workload 上，或者缺少已接受的 lever，kernel 仍被接受。
  - P8：设置了 BASE_OVERLAY_CMD，但 baseline 和 integrate legs 都没有 GEAK_OVERLAY_SHA。由于空栈被视为"可扩展"，全部通过，而 wfReturn 仍声称增量是在 s8 之上测得。这正是 4.17 要防的 confound（bare 与 stacked 增量分别为 4.27% 和 5.25%）。

- **对记录结果的影响**：无。触发需要 agent 出错或进入 deep 模式。

### 12. 状态与质量结论依赖 agent 自报，verifier 覆盖面不做检查
- **严重度**：medium（ORCH-A5、ORCH-A2、G-3 合并）
- **位置**：
  - `training_workflow.js:1784-1786`（status）
  - `462-505`（verifyDecision）
  - `1522-1575`（l0 / l1 / mgc 来自 Auditor）
  - `1334`（`sweep.l1`）
  - `scripts/verify_gate.py`
- **问题**：
  - Validate 自报 confirmed 且 delta 为 -3%，status 仍为 ok；什么都没接受时也是 ok。
  - verifier agent 只返回 primary pair 时，regression 否决就失效了（P1）。
  - `trajectory_gate compare`、`quality_ab_final` 都是纯 host Python，却从不重算。`--kind`、`--l0-strictly-better`（会把 step-1 floor 放宽 8 倍）和 `--band` 都由 agent 自选。
- **修复**：
  - status 由代码判定 `delta > band`（或由 verifier 重算），没有接受任何东西时返回 `no_gain`。
  - verifyDecision 用 REF_DIRS × CAND_DIRS 校验 pair 覆盖面。
  - gate_verifier 重算 L1：`--kind` 由 L0 的 out 是否 bit_identical 决定；`--l0-strictly-better` 必须有 oracle 输出的逐输出字段作依据。
  - 由 orchestrator 重算 quality_ab_final，并用 `/^PASS/` 推导 cleared（同时覆盖 ORCH-A8）。
- **对记录结果的影响**：无。属于信任模型缺口，没有已证实的错误接受。

## 二、系统性模式

1. **非对称的信任模型。** ORCH-1 只把"吞吐数字"改为独立重算。正确性、质量、packing 判定、运行 status、verifier 覆盖面仍采信 agent 自报的 JSON（第 1、3、12 条，以及 ORCH-A7 / A8）。本该由代码判定的结论交给了 agent 来"转述"。
2. **身份靠白名单和名称，不靠内容。** 涉及 argv/env 白名单（ID-1）、只哈希 impl.py（ID-2）、数据按路径（ID-8）、quality_reuse 只比参数表（第 2 条）、main_grad 用子串匹配（G-1）、缩写参数（ID-6）、原样字符串（ID-9）。每次发现一个漏洞只补一个键，同类问题反复出现。根本修法是从 realized 表和文件内容派生 identity，未知键 fail-closed。
3. **"独立复核"并不独立。** verifier 复制了同样的 NVTE 通配（ID-4），拿到的 band 更窄（MS-5），返回哪些 pair 由 agent 决定（ORCH-A2）。
4. **统计方法只在自身设计假设下被验证。** 校准只做均匀注入（MS-1），floor 在同一数据上调出（MS-4），两次查看没有做校正（G-4），K=8 是噪声 argmin（HFC-4），HF headline 的偏差随杠杆变号（MS-3）。
5. **关键不变量只写在 prompt 或 role card 中，并与代码脱节。** 包括 stacked baseline 和 carried config（第 11 条）、config_tuner 第 5 步、`cleared:null`、LEVER_ENV 文档有而代码无。
6. **交付物加固不对称。** Megatron bundle 有 harness 和 image pin，HF bundle 都没有，RESUME 却声称两者都有。
