# e2e_training_workflow — 两个月路线图（草案）

> 本文是 `ROADMAP.md` 的中文版。两份同步维护；如有出入，以英文版的数字为准。

撰写时的状态：`fast` 模式已端到端跑通。已完成 **3 次真实运行**（0.5B/2GPU ×1，7B/8GPU ×2），外加
**12 条 soak 腿**（11 条可用，1 条在第 1 步崩溃）。已接受 1 个 kernel，独立复测 **+4.66%**。

下面的排序由两个**本月实测确认**（而非假定）的约束决定：

**约束 A —— 不能判别的门，会让它之后的所有数字变成虚构。** 本月有 **3 个门在已经发出裁决之后**才被
发现不具判别力：吞吐门在 raw ratio 上接受（而窗口放置单独就能造出 +4.59%）；L1 包络会拒绝可证明干净
的腿（样本外零对照 3/3 失败）；L2 soak 放过了一个带 ×1.004 梯度偏置的 kernel。**因此本计划把"门"的
工作排在"优化"之前**——不是出于谨慎，而是因为在门本身可证伪之前，优化的产出根本无法被证伪。

**约束 B —— 一次运行耗时 8–10 小时，只产出约 2 个 head。** 最近一次 7B 运行：69 个 agent、1331 次
工具调用、8 小时 15 分、队列 4 个只做了 2 个、撞墙钟停止。按此速率，一个自然月**在独占机器的前提下**
约容纳 70–90 次运行——而机器并非独占，所以实际要按其中一小部分来规划。**限制第二个月的是迭代速度，
不是 agent 能力。**

假设（如不成立请指出，它们会实质改变计划）：单节点 8×MI308X 且共享；`rocm/primus:v26.4/5`；裸
Megatron + `--sft` 路径；暂无多机；精力主要投在本层而非其下的 kernel 层。

## 一、当前设计（as built）

### 分层结构

```
  training_workflow.js          ← 本层：系统封装。掌管身份、噪声带、门、预算
    ├─ 6 个 agent 角色          training_director · system_architect · profiler
    │                           kernel_extractor · convergence_auditor · integrator
    ├─ scripts/                 确定性的那一半：探针、汇总、比较、各道门、overlay
    ├─ workloads/*.env          缝 1 —— 固定的 workload 描述符（arch args、GBS/MBS/SEQ，
    │                           现在还包括该 workload 的 band floor）
    ├─ scripts/adapters/<stack>.sh   缝 2 —— 框架插槽（目前仅 megatron）
    └─ ../kernel_workflow/kernel_lane.js   未经改动的单 kernel 层，直接调用
                                （走 dispatcher 会耗掉运行时仅允许的那一层嵌套）
```

分工是刻意的：**判断归 agent，控制流归编排层。** 角色返回结构化 JSON，所有阈值由
`training_workflow.js` 施加。**没有任何 agent 能接受自己的候选。**

### 一次运行的流程

```
Setup      Director 测 3 次 TRUE 基线 → 跨 job 噪声带（R_cal）+ L1 轨迹 band
Profile    Profiler 跨 rank 分解 step：compute / exposed-comm / bubble / straggler，
           输出 Top-N，外加一份只读的配置诊断（fast 模式对 ConfigSweep 的替代，
           同时也就是 ConfigSweep 的需求清单）
Strategize Architect 按  cp_share × (1 − 1/attainable)  排序 —— 关键路径份额，
           不是 %GPU time。已验证：lmhead 预测 3.94%，实测 +4.66%
KernelTrack  逐个 head，直到 budget / gates / 墙钟耗尽：
             Extract   从实时捕获冻结 fwd+bwd oracle（绝不用回放）
             ↓ kernel_lane（递归，受 budget 限制）
             L0        算子级数值 vs 冻结的 fp32 oracle —— 只能拒绝
             Overlay   可逆重绑；逐 rank 证明前向与反向都已挂载
             L1        轨迹 —— 只能拒绝
             GATE      独占整机 A/B —— 唯一能"接受"的环节
             接受后：该候选成为被携带的参考，并触发重新 profile
             （瓶颈会移动 —— 已确认：接受 lmhead 后队列里出现了新 head）
Finalize   可逆 bundle + SHA256SUMS + 会自校验的 launch.sh
Report     architect 报告（写到仓库之外）
Validate   Director 独立复测并仲裁。**这才是官方数字。**
```

预算是三重的，且三者都在实战中触发过：`budget`（kernel 任务数）、`max_gates`（一次 A/B = 两次作业
启动，且会阻塞所有 lane）、以及来自 `args.t0_epoch_ms` 加 agent 读钟的墙钟（沙箱本身没有时钟）。

### 各道门的真实能力

**这张表是全文最重要的部分，每一行都是实测：**

| 门 | 能否 ACCEPT | 零对照 | 正对照 | 实测灵敏度 |
|---|---|---|---|---|
| **吞吐** | **能——唯一** | 47 对零差 0 假阳性 | 在已知 +4.66% 上触发 | 该真实配对 band 0.415%（旧公式 0.914%） |
| **L0** 算子数值 | 否（只拒绝） | ref-vs-ref 恰为 0 | **拒绝 ×1.004 偏置** | `scale_bias` 容差 2e-3；端到端 11.5 秒，比较本身约 40 毫秒 |
| **L1** step-1 探针 | 否 | 0.0%（位复现） | 抓到 attention 的 backward 缺陷 | 捕获 grad_norm 崩塌 −88.5% |
| **L1** 逐步包络 | 否 | **样本外 3/3 失败** | — | **advisory；W1 决定废弃还是修复** |
| **L2** soak | 否 | 通过 | **不拒绝 ×1.004** | 功效不足；约 0.9% 偏置，而非 0.4% |

贯穿其中的结论：**算子局部缺陷归 L0**（11.5 秒），**前向通路变化归 step-1 探针**（免费），而 soak 只
剩下两者都看不见的那部分。这正是 W3 存在的理由。

### 身份体系：反虚构的脊梁

`config_digest`（schema 3，33 个身份字段）回答"这两条腿测的是同一件事吗"；`impl_digest`（内容哈希）
回答"这是被 gate 过的那份实现吗"；`digest_schema` 给定义本身做版本。**v2 与 v3 刻意不可调和**——它要求
重新测量，因为 v2 的 sidecar 在物理上从未记录过 v3 所哈希的那些字段。

## 二、进度：已建成的，与**已验证**的

**已建成且在真实运行中验证**（三次训练运行共 134 个 agent，`agents_error: 0`）：

| 领域 | 状态 |
|---|---|
| 测量层 | **扎实。** `useful_tok_s_per_gpu`、warmup 检测、occupancy 守卫、污染重测、对齐的 `compare_legs.py`。正是它推翻了一个 +7.85% 的"胜利" |
| 六个角色 | 全部可执行；**拒绝路径与接受路径都已端到端走通** |
| 吞吐门 | 基于 47 对零差重标定；**两个对照均已实证** |
| L0 | 两个对照均已实证；两个新算子 oracle（attention varlen/GQA、lmhead+CE）经数值校验 |
| 提取 → kernel lane | 可用；孤立 kernel 上 18.86× geomean → 端到端 +4.66% |
| Overlay + engagement 证明 | 8 rank，前向与反向分别计数，零 fallback |
| Finalize bundle | 自校验；`launch.sh` 在校验和不符时拒绝启动 |
| 独立仲裁 | 独立角色（Director 或 Auditor）在**全部三次**运行中都推翻过上游结论 |

**已建成但尚不可信：**

- **L1 逐步包络** —— 样本外被证伪；默认 advisory（W1 定去留）
- **L2 soak** —— 工具与预注册规格都有，但**从未发出过有分量的裁决**

**尚未建成：**

- **ConfigSweep / `deep` 模式** —— 目前直接拒绝运行（W2）
- **本层的 `mode=bakeoff`** —— 结构上不可达，它需要运行时没有的那一层嵌套，只能从顶层驱动
- **多机** —— 未验证，且 overlay 机制明确无法存活
- **TP > 1** —— 现在是**明确拒绝**，而非静默出错（LM-head oracle 会冻结一个 shard 局部的 logsumexp）
- **第二个栈适配** —— 缝存在，但只有一个实现

### 第一个月的运行实际产出了什么

**14 个缺陷，分四类**（还不算若干随手修掉的小问题），而**分布本身就是结论**：

- **4 个直接阻塞启动**，且全是管道问题：一个多余的 `export`；一个沙箱根本没有的时钟；八个声明了却从未
  传入的 schema；三层嵌套而运行时只允许一层。
- **4 个是"门发出了自己撑不住的裁决"**。
- **3 个是身份/完整性漏洞**：`config_digest` 只覆盖五个字段；`impl_digest` 哈希的是路径；两次运行被
  合并进同一个 probe 目录。
- **3 个是静默错误默认值**：`--kind` 被忽略导致阈值紧了 40 倍；报告被写进仓库根目录；TP>1 未覆盖。

**没有一个是靠读代码发现的**，全部来自实际运行，以及坚持让每道门在已知输入上证明自己会失败。

## 三、第一个月：让它正确、完整、快到能迭代

### W1 —— 收口已诊断的门与反馈缺陷

门就是产品本身。三项，分析都已完成：

| 项目 | 依据 | 完成判据 |
|---|---|---|
| **给 L1 逐步包络定去留** | 一次会话内样本外被证伪两次（真差为零的配对上 5/5/6 步超限）；结构上看不见 +25% 的稳态 loss 位移，因为到第 12 步相同的腿本就差约 8.9% | 要么拿出一个能在 ≥3 个 workload 上通过样本外对照的包络，要么**正式废弃**它、并把 L1 记作 = step-1 探针 + 符号平衡。**不要让它半死不活地留着** |
| **把 attention 的 backward 缺陷回灌给 kernel 层** | step-1 grad_norm 74.109 → 8.524（−88.50%，噪声地板的 100–200 倍），而前向干净（p=0 配对 −0.1999%） | 拒绝时产出机器可读的诊断，供 kernel lane 作为起始约束；重跑该 head 不再从零重新发现 |
| **拒绝诊断进入 KB** | KB 学习卡片只记录**胜利**；attention 那次的隔离实验（p=0 匹配配对）是人工重新想出来的 | 被拒绝的候选也写卡片；下一个针对同算子的 lane 会读到 |

**为什么排第一**：这是唯一"分析已完成、只差管道"的一批；也正是它让 W2 产出的数字变得可信。

### W2 —— ConfigSweep / `deep` 模式

**最大的缺失功能。** `deep_mode: true` 目前**直接拒绝运行**，而 `fast` 模式的只读诊断早已在输出它的
需求清单：

- **71.3% 的 token 是 padding。** packing 直接抬高 `useful_tokens`；而 kernel 优化只能缩短
  `step_time`。**这在算术上是更大的杠杆**，并且它已经躺在每一次运行的诊断输出里了。
- `comm_overlap_pct = 0.0` —— 当前影响小，但随模型规模和 DP 度放大。

缝 1–6 已在 `fast` 中以平凡行为存在（DECISIONS 5.4），所以这是**接一个已设计好的缝**，不是新发明。

**完成判据**：一次 `deep` 运行能提出、测量并通过与 kernel 改动**同一套门**来 gate 至少一个配置改动，
且**内存转换**路径被走通（今天内存只能"存起来"，因为没有可以花它的旋钮）。

**风险**：配置改动按设计会改变 `config_digest`，所以每条 sweep 腿都是一个新身份。要为这套比较纪律
留预算，而不只是为 sweep 本身。

### W3 —— 让 L2 有资格说话，并找到 soak 真正的靶子

L2 在文档里有名字、会在 `risk_class: backward` 时自动触发，**却从未发出过有分量的裁决**。两次运行
（约 11 小时）都以 ADVISORY 收场。

依据前述证据的重新定位：**算子局部数值是 L0 的职责**——L0 用 11.5 秒拒绝 ×1.004 偏置，而两次 300 步
soak 完全漏掉。所以 soak 的正对照必须是 **L0 结构上看不见**的那一类缺陷（L0 只评估一个冻结的
microbatch）：

- 跨步状态污染（被接受的 lmhead kernel 会累加进 `main_grad`——**正是这一类**）
- 只在约 19200 次调用后才累积出来的误差
- allocator / 碎片化效应
- 单次调用会被平均掉、但整个 epoch 不会的非确定性

**完成判据**：构造出该类别的正对照，soak **能拒绝它**，而 L0 **放行它**。在两半都成立之前，
**soak 保持不跑**——约 10 小时却无法证明自身灵敏度，是负收益。

### W4 —— 先买迭代速度，再补覆盖

**速度（约束 B）。** 现状：每次运行 Setup 要测 3 条基线腿（7B 约 25 分钟），且每次都从裸栈重新
profile。候选方案：

- 以 `config_digest` + `digest_schema` 为键持久化并复用基线（schema 3 之后 digest 才真正覆盖身份）
- 从 `unexplored_heads` 续跑一次被中止的运行，而不是重新推导队列
- 在 barrier 允许处把 lane 工作与 gate 腿重叠

**完成判据**：**同样墙钟下每轮 ≥3 个 head**，实测为准。

**覆盖。** 两个已知缺口，目前都是**拒绝**而非出错——这是正确状态，但限制了适用范围：

- **TP > 1**：LM-head 捕获现已拒绝（否则 oracle 会冻结 shard 局部 logsumexp）。解禁需要一个
  vocab-parallel 参考实现。
- **packed 数据**：已接受的 +4.66% 依赖约 70% 的 padding，**在 packed 上会趋近于零**。目前任何
  超出"带 padding 的 SFT"的结论都没有依据。

## 四、第二个月：适配不同 case 与训练框架

第二个月假定第一个月交付了**可信的门**与**每轮 ≥3 个 head**。**若未达成，不要开始第二个月**——把一个
不能判别的仪器适配到多个栈上，只会把虚构复制多份。

### W5–6 —— 第二个训练栈

`scripts/adapters/<stack>.sh` 是一个已设计的缝，但**只有一个实现，因此未经验证**：一个实现无法暴露
哪些假设泄漏了。候选按价值粗排：Primus（同机，距离最近）、TorchTitan / DeepSpeed（抽象不同、更难，
因而信息量更大）。

第二个适配真正测试的是什么（所以这不是白工）：

- **探针**是否真的与栈无关？它之所以存在，是因为上游 Megatron 根本不报 tokens/s；一个**自己会报**
  的栈，会暴露我们的数字是否可比。
- **配置 IR** 是否经得起，还是只是披着 IR 外衣的 Megatron 词汇表（DECISIONS 6.1）？
- **能力清单**路由是否正确——它已经抓到过一次过度声明（`step_ranged_profiler`）。

**完成判据**：在第二个栈上接受 1 个 kernel，经由**同一套门**，且适配 diff **局限在
`scripts/adapters/` 内**。任何被迫在该目录之外的改动都是泄漏，须如实记录。

### W7 —— 其它 case

按"每 GPU 小时的信息量"粗排：

| case | 为什么 | 大概会打破什么 |
|---|---|---|
| **packed 序列** | 已知最大的杠杆，也是当前结论明写的限制 | 跨 segment 的 attention 隔离；rope/varlen 路径在 MBS=1 时就已需要 squeeze |
| **TP > 1 / PP > 1** | `config_digest` 声称覆盖并行映射，而它在**任何已测的腿上都没真正覆盖过** | vocab-parallel 参考；逐 rank 捕获；straggler 桶（TP1×DP8 下为空，更高时未测） |
| **不同模型族**（如 MoE） | head 算子的**类别**本就随规模变化（0.5B → attention bwd；7B → GEMM） | 路由/专家算子没有 oracle；关键路径模型假定 dense |
| **更长序列 / 不同精度** | 改变整个排序所依赖的算术强度 | fp8 需要新的 L0 容差——现有容差锚定在原实现自身的 bf16 误差上 |

### W8 —— 调优与 campaign 模式

- **campaign 模式**：多个 workload、一份预算、KB 跨运行携带。KB 身份已按 `config_digest` 哈希
  （缝 6），比看上去更接近。
- **逐 workload 类别复核噪声带。** `ACROSS_JOB_FLOOR_PCT` 现已落在 `workloads/*.env`（7B 0.15%，
  0.5B 0.5%），来自 47 对实测零差。每个新 workload 都需要自己的值；而**最便宜的杠杆始终是窗口长度，
  不是 band**：≥29 个稳态步让 0.5B 的噪声地板减半。
- **收掉剩余三个 head**（swiglu 1.13%、mlp_gate_up 1.05%、rope 0.78%）——等运行便宜到约 1% 的条目
  也值得占用一次 gate 时再做。

## 五、每周都适用的横向纪律

- **没有两个对照，门就不上线。** 一个它必须通过的零对照，一个它必须失败的正对照。本月靠这条抓到 3 个
  缺陷，成本相比它省下的东西可以忽略。
- **阈值必须在判定它的数据之前预注册。** 它奏效了：两条 L2 判据后来被证明有缺陷，被**撤回**而**没有
  回头去调 K**。
- **运行产物不进仓库。** 曾有一份报告落到仓库根目录，只因为角色卡没写路径。
- **DECISIONS.md 里每条主张都要指名一个数字及其来源。** 保持下去——这正是本月那些错误拐点**可被发现**
  的原因。

## 六、已知风险

1. **共享机器。** 污染已有处理（有界重测，耗尽则致命），但它让吞吐不可预测地封顶，而第二个月的排期
   假定了大量 GPU。
2. **单节点。** 多机未验证，且 overlay 机制明确无法存活（单节点上 `torchrun` 继承父环境；多机需要
   逐节点物化）。
3. **混沌就是噪声地板。** 实测：在**单次运行内**做任何平均都买不到功效，因为发散是序列相关的。未来
   任何收敛性工作只能用**加腿**买功效，加步数不行——**这是问题的永久属性，不是当前限制。**
4. **本计划偏重"门"，读起来可能显得慢。** 反证就是本月本身：headline 数字经受住了每一次审计，而三个
   门没有。**风险一直在门这边。**
