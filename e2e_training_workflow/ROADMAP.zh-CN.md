# e2e_training_workflow — 两个月路线图（草案）

> 本文是 `ROADMAP.md` 的中文版。两份同步维护；如有出入，以英文版的数字为准。

状态，**2026-10-08 修订**（初稿 2026-09-24）。`fast` 模式已端到端跑通。**5 次真实运行**
（0.5B/2GPU ×1，7B/8GPU ×4），外加 12 条 soak 腿和一次 4 腿合并栈测量。

**已接受 2 个 kernel，合并栈实测 +12.36%** —— 四种 ref/cand 配对极差 0.12 个点，零对照 +0.0706%，
窗口免疫的 `step_median_ms` 交叉校验 +12.324%。两者的收益**复利**（相加预测 +12.00%，复利 +12.34%，
实测 +12.36%），说明它们缩短的是 step 中**不重叠**的部分。

下面的排序由两个**实测**（而非假定）的约束决定：

**约束 A —— 不能判别的门，会让它之后的所有数字变成虚构。** 本月有 **3 个门在已经发出裁决之后**才被
发现不具判别力：吞吐门在 raw ratio 上接受（而窗口放置单独就能造出 +4.59%）；L1 包络会拒绝可证明干净
的腿（样本外零对照 3/3 失败）；L2 soak 放过了一个带 ×1.004 梯度偏置的 kernel。**因此本计划把"门"的
工作排在"优化"之前**——不是出于谨慎，而是因为在门本身可证伪之前，优化的产出根本无法被证伪。

**约束 B —— 一次运行 8–10 小时、决断约 2 个 head，而且这一点没有改变。** 去掉开销后运行从 10.6 小时
降到 7.9 小时，**head 数两次都是 2**。时间线解释了原因：`kernel_lane` 占一次运行的 **46%**，而它就是
真正的优化工作本身。单个 head 约 2.5–3 小时，这不是开销。**原定的完成判据（每轮 ≥3 个 head）是错的
目标**——见下文"这份计划错在哪"。

假设（如不成立请指出，它们会实质改变计划）：单节点 8×MI308X 且共享；`rocm/primus:v26.4/5`；裸
Megatron + `--sft` 路径；暂无多机；精力主要投在本层而非其下的 kernel 层。

## 一、当前设计（as built）

### 分层结构

```
  training_workflow.js          ← 本层：系统封装。掌管身份、噪声带、门、预算
    ├─ 6 个 agent 角色          training_director · system_architect · profiler
    │                           kernel_extractor · convergence_auditor · integrator
    ├─ scripts/                 确定性的那一半：探针、汇总、比较、各道门、overlay
    ├─ workloads/*.env          缝 1 —— 固定的 workload 描述符（arch args、GBS/MBS/SEQ，
    │                           现在还包括该 workload 的 band floor）
    ├─ scripts/adapters/<stack>.sh   缝 2 —— 框架插槽（目前仅 megatron）
    └─ ../kernel_workflow/kernel_lane.js   未经改动的单 kernel 层，直接调用
                                （走 dispatcher 会耗掉运行时仅允许的那一层嵌套）
```

分工是刻意的：**判断归 agent，控制流归编排层。** 角色返回结构化 JSON，所有阈值由
`training_workflow.js` 施加。**没有任何 agent 能接受自己的候选。**

### 一次运行的流程

```
Setup      Director 测 3 次 TRUE 基线 → 跨 job 噪声带（R_cal）+ L1 轨迹 band
Profile    Profiler 跨 rank 分解 step：compute / exposed-comm / bubble / straggler，
           输出 Top-N，外加一份只读的配置诊断（fast 模式对 ConfigSweep 的替代，
           同时也就是 ConfigSweep 的需求清单）
Strategize Architect 按  cp_share × (1 − 1/attainable)  排序 —— 关键路径份额，
           不是 %GPU time。已验证：lmhead 预测 3.94%，实测 +4.66%
KernelTrack  逐个 head，直到 budget / gates / 墙钟耗尽：
             Extract   从实时捕获冻结 fwd+bwd oracle（绝不用回放）
             ↓ kernel_lane（递归，受 budget 限制）
             L0        算子级数值 vs 冻结的 fp32 oracle —— 只能拒绝
             Overlay   可逆重绑；逐 rank 证明前向与反向都已挂载
             L1        轨迹 —— 只能拒绝
             GATE      独占整机 A/B —— 唯一能"接受"的环节
             接受后：该候选成为被携带的参考，并触发重新 profile
             （瓶颈会移动 —— 已确认：接受 lmhead 后队列里出现了新 head）
Finalize   可逆 bundle + SHA256SUMS + 会自校验的 launch.sh
Report     architect 报告（写到仓库之外）
Validate   Director 独立复测并仲裁。**这才是官方数字。**
```

预算是三重的，且三者都在实战中触发过：`budget`（kernel 任务数）、`max_gates`（一次 A/B = 两次作业
启动，且会阻塞所有 lane）、以及来自 `args.t0_epoch_ms` 加 agent 读钟的墙钟（沙箱本身没有时钟）。

### 各道门的真实能力

**这张表是全文最重要的部分，每一行都是实测：**

| 门 | 能否 ACCEPT | 零对照 | 正对照 | 实测灵敏度 |
|---|---|---|---|---|
| **吞吐** | **能——唯一** | 47 对零差 0 假阳性 | 在已知 +4.66% 上触发 | 该真实配对 band 0.415%（旧公式 0.914%） |
| **L0** 算子数值 | 否（只拒绝） | ref-vs-ref 恰为 0 | **拒绝 ×1.004 偏置** | `scale_bias` 容差 2e-3；端到端 11.5 秒，比较本身约 40 毫秒 |
| **L1** step-1 探针 | 否 | 0.0%（位复现） | 抓到 attention 的 backward 缺陷 | 捕获 grad_norm 崩塌 −88.5% —— **L1 仅剩的检测器** |
| **L1** 符号平衡 | 否 | **真实零差配对打出 0.000** | — | 已约束在实测干净范围内；分不清修复与缺陷 |
| **L1** 逐步包络 | 否 | **样本外 3/3 失败** | — | **2026-09-28 已废弃投票权** |
| **L2** soak | 否 | 通过 | **不拒绝 ×1.004** | 功效不足；约 0.9% 偏置，而非 0.4% |

贯穿其中的结论：**算子局部缺陷归 L0**（11.5 秒），**前向通路变化归 step-1 探针**（免费），而 soak 只
剩下两者都看不见的那部分。这正是 P4 存在的理由。

### 身份体系：反虚构的脊梁

`config_digest`（schema 3，33 个身份字段）回答"这两条腿测的是同一件事吗"；`impl_digest`（内容哈希）
回答"这是被 gate 过的那份实现吗"；`digest_schema` 给定义本身做版本。**v2 与 v3 刻意不可调和**——它要求
重新测量，因为 v2 的 sidecar 在物理上从未记录过 v3 所哈希的那些字段。

## 二、进度：已建成的，与**已验证**的

**已建成且在真实运行中验证**（五次训练运行约 260 个 agent，`agents_error: 0`）：

| 领域 | 状态 |
|---|---|
| 测量层 | **扎实。** 正是它推翻了一个 +7.85% 的"胜利"，也是回答头条问题的那把尺子 |
| 六个角色 | 全部可执行；接受、拒绝、**整合受阻**三条路径都已端到端走通 |
| 吞吐门 | 基于 47 对零差重标定；**两个对照均已实证** |
| L0 | 两个对照均已实证；四个算子 oracle；11.5 秒拒绝 ×1.004 梯度偏置 |
| 提取 → kernel lane | 可用；孤立 kernel 18.86× geomean → 端到端 +4.66% |
| Overlay | **现在是栈** —— `GEAK_OVERLAY` 接受列表，全有或全无，逐 overlay 计数 |
| 合并交付 | `measure_stack.sh`；**实测 +12.36%，8 rank 上逐 overlay 证明 engagement** |
| 独立仲裁 | 独立角色在**全部五次**运行中都推翻过上游结论 |

**已决断的 head**（7B）：

| head | 结果 |
|---|---|
| `lmhead_ce_unmasked_gather` | **接受，+4.66%** |
| `mlp_fc2_down` | **接受，+7.34%** —— wgrad 比原实现更接近 fp32 十三倍 |
| `attn_fmha_fwdbwd_gqa_d128_causal` | 拒绝 —— backward 缺陷，step-1 grad_norm −88.50% |
| `mlp_fc1_swiglu` | 拒绝 —— 第 2 个 iteration 产生 inf 梯度，复现两次 |
| `attn_dense_wgrad_rowslice` | `no_win`：**+1.147%** vs band 2.467% —— **可回收，见下** |
| `attn_fmha_bwd_retry` | 被一个事后证明不具判别力的检测器拒绝 —— **悬而未决** |

**已建成但不可信，而且情况比之前更糟：**

- **L1 现在实际上只剩 step-1 探针。** 逐步包络已废弃投票权（4 次运行、4 次触发、0 次成立）。
  **一周之内，另一个投票检测器——早窗符号平衡——以同样方式被证伪**：一对**真实差异恰为零**的腿
  打出 0.000。现在它被约束在实测的干净配对范围内，但更深的问题已记录且未解决——**符号检验无法区分
  "真修好了 bug 所以下降更快"和"一个朝下的系统性偏置"**，而它拒绝的那个候选，L0 判定其**比现任
  实现严格更准确**。
- **L2 soak** —— 工具与预注册规格都有，**从未发出过有分量的裁决**。

**尚未建成：** ConfigSweep / `deep` 模式 · 本层的 `mode=bakeoff`（结构上不可达）· 多机 ·
TP > 1（是拒绝，不是支持）· 第二个栈适配。

### 躺在磁盘上的可回收价值

两个候选**已被测量**，却因仪器缺陷而丢失，而那些缺陷现已修复。重新 gate 各约 1 小时，
相比决断一个全新 head 约 3 小时：

- **`attn_dense_wgrad_rowslice`，+1.147%。** 被拒是因为复用的噪声基线腿（IQR 1.842%，兄弟腿
  0.05–0.11%）把 band 抬到 2.467%。参考腿现在取最安静的那条，同样的腿会把 band 定在 0.5% 附近。
  该 overlay 已通过 L0。
- **`attn_fmha_bwd_retry`。** 唯一否决依据是几天后被证伪的符号检验，而 L0 判定它比现任实现**严格更
  准确**——现任实现违反一个解析 `dq` 不变量达 **1355.79 倍**。**这一个需要的是决断，不只是重跑**：
  它是 L0 与 L1 公开冲突、而框架没有规则的那个具体案例。

## 这份计划错在哪

值得记录，因为这些错误比按计划走通的部分更有用。

**1.「每轮 ≥3 个 head」是错的完成判据。** 去开销确实奏效（10.6h → 7.9h），**head 数没动**，因为
`kernel_lane` 占 46% 而它就是工作本身。追求 head/轮 意味着削减优化深度去让一个数字变好看。有用的
指标是**每个"已决断 head"（含被拒绝的）的成本**；在这个指标下真正的杠杆是**不再重复推导已有答案**
（`skip_heads`、`baseline_dirs`），而不是跑得更快。

**2. 这份计划审计了"决策路径"，却从未看过"交付路径"。** 计划里没有任何一处注意到两个已接受的
kernel **无法一起运行**——`GEAK_OVERLAY` 只接受一个 manifest，而两个 overlay 重绑不同符号。系统能
接受 N 个候选，却无法把它们作为一个栈交付。**一个为"做决断的系统"写的 roadmap，应当在每个阶段都问：
它决断出来的东西后来怎么了。**

**3.「给包络定去留」问题提得太小。** 决断它的过程暴露出问题不在某一个检测器：符号检验一周内栽在了
同一个对照上。正确的问题是**"L1 到底能检测什么？把无法证明的部分移除后还剩什么？"**——答案是：
step-1 探针，外加一个分不清修复与缺陷的符号检验。

## 三、剩余工作，按优先级

### 第一个月对照原计划

| 周 | 项目 | 状态 |
|---|---|---|
| W1 | 给 L1 包络定去留 | ✅ **已废弃投票权**，基于四次运行的证据 |
| W1 | attention 缺陷回灌 kernel 层 | ✅ 两条通道（运行内约束、跨运行 KB 卡片） |
| W1 | 拒绝诊断进 KB | ⚠️ **有缺口**：仅在 L0/L1 失败时触发，所以 **inf 梯度**那个候选——最灾难的失败模式——没有产生卡片 |
| W2 | ConfigSweep / `deep` | ❌ 未开始 |
| W3 | L2 正确类别的正对照 | ❌ 未开始 |
| W4 | 迭代速度 | ⚠️ 10.6h → 7.9h，head 数未变；判据本身是错的（见上） |
| W4 | TP>1、packed 覆盖 | ❌ 仍是拒绝 / 未动 |
| — | **多 overlay 交付 + 合并测量** | ✅ **计划外，也是这段时间最有价值的产出** |

### P1 —— 在干净腿上重测 `attn_dense_wgrad_rowslice`（约 40 分钟）

**对本计划初稿的更正。** P1 原本写的是"+1.147% 输给了被复用的噪声基线腿，取最安静腿即可回收"。
动手前查证推翻了它：2.467% 的 band 来自 **gate 腿自身**的离散度——参考腿 IQR **3.324%**、候选腿
1.316%——而同一 workload 正常是 0.05–0.11%。基线腿的修复对此毫无作用。

查证发现的问题更糟也更有用：这次运行报的是 **`no_win`**，而真相是**"我们没能测"**。band 达到
workload floor 的 **16.4 倍**，即门槛由腿而非 workload 决定；换成干净腿，同样的 delta 直接越过
0.15% 的 floor。现已修复——该情形下 `gateVerdict` 返回 `inconclusive_noise` 并带 `remeasure: true`，
且**不计入停止规则**，因为一条噪声大到测不出的腿，对"候选是否有收益"这件事什么也没说。

所以 P1 是一次**重测**而非重算：一对干净腿的 A/B。overlay 还在磁盘上，且已通过 L0。

### P2 —— 为 L0/L1 冲突立规则，然后再决断 `attn_fmha_bwd_retry`

这是**框架缺口，不是候选问题**，而且它会复发。L0 说候选在每个输出上都比现任严格更准确；L1 的符号
检验因为它单向下降而拒绝。两句话都是真的。框架没有规则，于是今天的裁决取决于**先读哪一层**。

一条可辩护的规则，**必须在应用到这个候选之前先写下来**：**当 L0 判定候选在所有输出上都比现任严格
更准确时，单向的 loss 改善属于佐证而非偏置证据，符号检验不得仅凭此拒绝。** 它绝不能覆盖的危险情形
是：候选**更不准确**却下降更快。

### P3 —— ConfigSweep / `deep` 模式（剩余最大杠杆，且差距明显）

7B 上的 kernel 轨道正在肉眼可见地收敛：队列预期从 5.82% 掉到 **1.37% / 1.24%**。而每一次运行都在
报告同一个未被利用的机会：**70.1% 的 token 是 padding**。packing 直接抬高 `useful_tokens`，而
kernel 优化只能缩短 `step_time`——剩下的 head 每个约值 1%。

缝 1–6 已在 `fast` 中以平凡行为存在，所以这是**接一个已设计好的缝**。
**完成判据**：一次 `deep` 运行用与 kernel 改动**同一套门**gate 住至少一个配置改动，且内存转换路径被走通。

**排序说明：P3 必须排在 P2 之后。** 配置改动按设计会改变 `config_digest`，每条 sweep 腿都是新身份；
在 gate 规则未定时开始，等于把两个未知量叠加。

### P4 —— L2 soak，卡在缺少正确的正对照

结论不变且依然成立：soak 的正对照必须是 **L0 结构上看不见**的那一类缺陷——跨步状态、约 19200 次调用
才累积出的误差、allocator 效应。L0 用 11.5 秒拒绝的算子局部偏置，两次 300 步 soak 完全漏掉。
**在这样的正对照存在、且 soak 能拒绝它之前，不要再跑 soak。**

### P5 —— 补上 W1 发现的 KB 缺口

一个在第 2 个 iteration 以 inf 梯度死掉的候选**不会写任何 KB 卡片**，因为规则只在
`l0.pass == false || l1.pass == false` 时触发，而整合失败两者都不是。**最灾难的失败模式，恰恰是
知识库永远听不到的那个。**

## 四、第二个月：适配不同 case 与训练框架

第二个月假定第一个月交付了**可信的门**与**每轮 ≥3 个 head**。**若未达成，不要开始第二个月**——把一个
不能判别的仪器适配到多个栈上，只会把虚构复制多份。

### W5–6 —— 第二个训练栈

`scripts/adapters/<stack>.sh` 是一个已设计的缝，但**只有一个实现，因此未经验证**：一个实现无法暴露
哪些假设泄漏了。候选按价值粗排：Primus（同机，距离最近）、TorchTitan / DeepSpeed（抽象不同、更难，
因而信息量更大）。

第二个适配真正测试的是什么（所以这不是白工）：

- **探针**是否真的与栈无关？它之所以存在，是因为上游 Megatron 根本不报 tokens/s；一个**自己会报**
  的栈，会暴露我们的数字是否可比。
- **配置 IR** 是否经得起，还是只是披着 IR 外衣的 Megatron 词汇表（DECISIONS 6.1）？
- **能力清单**路由是否正确——它已经抓到过一次过度声明（`step_ranged_profiler`）。

**完成判据**：在第二个栈上接受 1 个 kernel，经由**同一套门**，且适配 diff **局限在
`scripts/adapters/` 内**。任何被迫在该目录之外的改动都是泄漏，须如实记录。

### W7 —— 其它 case

按"每 GPU 小时的信息量"粗排：

| case | 为什么 | 大概会打破什么 |
|---|---|---|
| **packed 序列** | 已知最大的杠杆，也是当前结论明写的限制 | 跨 segment 的 attention 隔离；rope/varlen 路径在 MBS=1 时就已需要 squeeze |
| **TP > 1 / PP > 1** | `config_digest` 声称覆盖并行映射，而它在**任何已测的腿上都没真正覆盖过** | vocab-parallel 参考；逐 rank 捕获；straggler 桶（TP1×DP8 下为空，更高时未测） |
| **不同模型族**（如 MoE） | head 算子的**类别**本就随规模变化（0.5B → attention bwd；7B → GEMM） | 路由/专家算子没有 oracle；关键路径模型假定 dense |
| **更长序列 / 不同精度** | 改变整个排序所依赖的算术强度 | fp8 需要新的 L0 容差——现有容差锚定在原实现自身的 bf16 误差上 |

### W8 —— 调优与 campaign 模式

- **campaign 模式**：多个 workload、一份预算、KB 跨运行携带。KB 身份已按 `config_digest` 哈希
  （缝 6），比看上去更接近。
- **逐 workload 类别复核噪声带。** `ACROSS_JOB_FLOOR_PCT` 现已落在 `workloads/*.env`（7B 0.15%，
  0.5B 0.5%），来自 47 对实测零差。每个新 workload 都需要自己的值；而**最便宜的杠杆始终是窗口长度，
  不是 band**：≥29 个稳态步让 0.5B 的噪声地板减半。
- **收掉剩余三个 head**（swiglu 1.13%、mlp_gate_up 1.05%、rope 0.78%）——等运行便宜到约 1% 的条目
  也值得占用一次 gate 时再做。

## 五、每周都适用的横向纪律

- **没有两个对照，门就不上线。** 一个它必须通过的零对照，一个它必须失败的正对照。本月靠这条抓到 3 个
  缺陷，成本相比它省下的东西可以忽略。
- **阈值必须在判定它的数据之前预注册。** 它奏效了：两条 L2 判据后来被证明有缺陷，被**撤回**而**没有
  回头去调 K**。
- **运行产物不进仓库。** 曾有一份报告落到仓库根目录，只因为角色卡没写路径。
- **DECISIONS.md 里每条主张都要指名一个数字及其来源。** 保持下去——这正是那些错误拐点**可被发现**的原因。
- **审计交付路径，不只是决策路径。** 两个已接受的 kernel 有两周时间无法一起运行而无人察觉，因为所有
  检查问的都是"这个裁决成立吗"，没有一个问"我们接受的东西能交付吗"。
- **写下告诫与遵守告诫是两回事。** 合并栈测量第一次失败，栽的正是 bundle 自己的 `launch.sh` 警告过、
  且 `l2_soak.sh` 已经防住的"manifest 必须 per-run"那个坑——两处都是本项目自己写下的。

## 六、已知风险

1. **共享机器。** 污染已有处理（有界重测，耗尽则致命），但它让吞吐不可预测地封顶，而第二个月的排期
   假定了大量 GPU。
2. **单节点。** 多机未验证，且 overlay 机制明确无法存活（单节点上 `torchrun` 继承父环境；多机需要
   逐节点物化）。
3. **混沌就是噪声地板。** 实测：在**单次运行内**做任何平均都买不到功效，因为发散是序列相关的。未来
   任何收敛性工作只能用**加腿**买功效，加步数不行——**这是问题的永久属性，不是当前限制。**
4. **本计划偏重"门"，读起来可能显得慢。** 反证就是这段时间本身：headline 数字经受住了每一次审计——
   而且现在是**实测的 +12.36%**，不是算术推断——与此同时**五个**门或检测器没能撑住。**风险一直在门这边。**
5. **L1 很薄，项目应当直说。** 两次废弃之后，它只剩一个零噪声探针加一个分不清修复与缺陷的符号检验。
   **轨迹层面的信心目前建立在 L0 很强，而不是 L1 很强。**
